# QA release and recovery

Use GitHub Actions → **Deploy MangoRTS QA** on `main`, choose `deploy`, and provide its exact 40-character commit. Approval includes that commit's pending SQL through `miraeopus-migrate`; no separate SQL engine or direct database credential is used. `bootstrap-images` still only registers bootstrap artifacts and creates no GitHub deployment record. Fresh schema initialization and DEV-to-QA copying remain separate human operations.

The coordinator builds and tests before downtime. It reads a structured migration plan, archives the actual previous frontend under `mangorts/qa/releases/<release-id>/frontend` in the existing private Terraform-state bucket, pins previous backend images by digest, and saves nonsecret ECS configuration and migration fingerprints. The migration ledger records filenames, not historical checksums; the runner stops on unknown history and known conflicting one-time schema targets rather than inventing ledger entries.

Maintenance closes the ALB gate, fences old attachment upload URLs and delayed scheduled cleanup, disables schedules, drains services, and stops standalone QA tasks. The stopped migration plan must match preflight. If SQL is pending, the coordinator waits at most 20 minutes for the existing RDS automated backup window to cover the stopped-writer timestamp before invoking any migration. RDS reports its latest point through `DescribeDBInstances` and its complete window through `DescribeDBInstanceAutomatedBackups`. A UTC timestamp alone does not authorize SQL. No normal release creates a snapshot, database copy, or second database. [AWS PITR documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html).

Terraform applies only the enumerated release resources; a plan changing another foundation resource or deleting a non-task resource stops. API and worker desired counts and schedules remain paused during that apply. After SQL and ledger verification, only the new API starts behind the maintenance gate. The coordinator publishes the built frontend, verifies matching revisions and Cognito boundaries, runs the finite attachment cleanup task to successful completion, and then reopens traffic and schedules. Anonymous auth checks do not prove an authenticated user's full UI journey.

## Recovery

Failures automatically attempt recovery after first closing and draining QA. Cancellation leaves maintenance in place. The workflow summary gives the exact release ID. To recover a successfully deployed bad release, select `recover` in the same action, approve the current main commit containing the coordinator, and enter the current retained release ID. Recovery rejects a superseded release. Inspect the recorded failure and the exact migration plan before retrying; missing or conflicting history requires separate human investigation.

If neither SQL nor new application code started, recovery verifies unchanged database state and restores the previous code/frontend without creating a database. Otherwise it verifies that the saved recovery boundary is still available, creates `mangorts-qa-recovery-<release-id>` with RDS PITR, and restores attachment state at that same time. QA test changes after that boundary are discarded. This applies to code-only releases too because application startup and cleanup can change data. Code-only normal deployment makes no additional backup and waits for coverage only if actual recovery becomes necessary.

Terraform continues to own and protect the original database. A restored instance is explicitly owned by the recovery coordinator and tagged `managed_by=qa-release-recovery`; it is not silently imported over the original resource. The nonsecret SSM parameter `/mangorts/qa/active-database-identifier` selects the active database. Every later Terraform plan reads that parameter and validates the selected private PostgreSQL 17 instance's exact subnet and security groups. Terraform ignores changes to the parameter's value so a later apply cannot reverse recovery. Both original and restored databases remain deletion-protected. Retiring an old database is a separately approved human action; duplicate running cost exists only after an actual recovery, until that action.

Recovery checks the restored schema fingerprint and migration ledger, recreates the captured code configuration with the recovered endpoint and immutable old image, restores actual frontend files, and restores the captured schedule target. A release predating the attachment lock keeps the new daily cleanup disabled. Failed recovery leaves the API gate, services, schedules, and attachment writers in maintenance with a saved error. Do not bypass these gates to make a green health check.

## Attachments, effects, and retention

QA attachment versioning must be bootstrapped once, with its 15-minute propagation period complete before a release boundary. Direct presigned writes must be fenced while establishing that initial boundary and while recovering. Recovery copies the historical object version into a new current version or adds a delete marker; it never deletes historical attachment versions. It validates the full plan first and refuses ambiguous timestamps, more than 100,000 historical entries, or a required copy larger than 5 GB. Those cases require human investigation while QA remains paused. [AWS S3 versioning behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/versioning-workflows.html).

The current recovery record pins its required backend and migration images with `qa-recovery-` tags in the existing ECR repository. The QA lifecycle protects these tags from its ordinary 50-image expiration rule; a newer captured release removes superseded recovery tags. Thus repeated failed image builds cannot expire the current recovery artifacts.

Noncurrent attachment versions are retained for the database backup period plus one day. Release records and frontend archives use the same bounded period, with the current recovery record retained until superseded. Subsequent releases prune expired record versions only under the QA release prefix; no shared Terraform state, database backup, or attachment version is deleted by this pruning. Restorability still ends at the actual RDS window, even if a release record remains.

Database/S3 restoration does not recall delivered email or undo provider-side effects. Review such effects separately; recovery must not resend messages to compensate automatically.
