# Attachment deletion recovery rollout

Repository wiring is **not deployed recovery**. This change has not applied a database migration, changed AWS, or enabled a live schedule. Dev and QA each need the following human rollout before their API loses the minute timer. Production infrastructure is outside this change.

Recovery handles attachments already marked deleted. The existing full-user-deletion path in `postgres_auth.go` can remove personal email messages without retiring their attachment links; personal draft/signature cleanup also needs a separate auth change. Those attachments remain unmarked, so neither the old timer nor this recovery task repairs that preexisting defect. This focused change leaves auth untouched.

The API and email worker wake cleanup after successful deletion commits and run recovery at startup. A private Fargate task runs `MANGORTS_RUNTIME_ROLE=attachment-maintenance` once daily through EventBridge, independently of the email service. It uses the same image, database secret selector, attachment bucket, task roles, subnets, and security group as that environment's API. It initializes no HTTP, auth, email, or realtime service.

Actual cleanup failures retry after increasing delays from one minute to one hour. New deletion events coalesce during that delay and wait for the scheduled retry, so busy editing cannot repeatedly retry a broken storage request. A successful settled pass returns to waiting without a database query.

Cleanup and deterministic email re-import use the same PostgreSQL transaction lock for each exact company/attachment. Re-import checks the row before writing bytes under that lock, preserving a live attachment and rejecting a pending one until cleanup finishes. This prevents a delayed duplicate deletion from removing re-imported bytes at the reused object key.

Older images do not take this lock. The initial rollout requires an approved maintenance window: stop all older API, email-worker, and standalone cleanup/import processes before enabling or running new recovery. Keep them stopped until recovery is proven and only the new image is ready to resume service. The new lock cannot protect bytes from an older process that ignores it.

Each recovery run examines at most 10,000 attachments in pages of 100, with a 15-minute cleanup deadline and a 16-minute process deadline including startup. A failed item, query, time limit, interruption, or unfinished cap exits nonzero. There is no daemon, attachment queue, or frequent recovery scan. An exceptional lost wake can leave inaccessible bytes until the next successful daily run; an outage or failed daily run can extend that delay until operators restore recovery.

## Required rollout order

1. Use the environment's approved human AWS SSO and database operator access. Confirm the current deployment image and save it as the rollback image. Confirm the environment's Terraform state and non-secret inputs using its existing [dev](mangorts-deploy-runbook.md) or [QA](mangorts-qa-environment-runbook.md) runbook. Do not obtain or copy writer passwords into local files.
2. Run the complete `backend/db/migrations/20260905_attachment_pending_deletion_index.sql` file in DBeaver against the intended PostgreSQL 17 database. It reports the server version and creates the pending-only index inside one atomic, version-checked statement; stop on its unsupported-version result. The index build briefly blocks attachment writes, so use an approved quiet window. Apply no other schema change for this cleanup patch.
3. Build and publish an immutable backend image containing this change through the existing authorized release process. Record its URI and revision, and arrange the maintenance window before recovery bootstrap.
4. In `infra/aws-dev` or `infra/aws-qa`, initialize Terraform against that environment's existing `backend.hcl`. Set `backend_image_uri` and `deploy_revision` to the new image/revision for the bootstrap plan. Set `attachment_maintenance_alarm_action_arns` to approved existing notification targets if notifications are required; its empty default still creates visible CloudWatch alarms but sends no notification. Use the human SSO role to bootstrap the new narrowly scoped deploy policy, EventBridge role, and log resource policy.
5. During the approved maintenance window, drain and stop the existing API and email-worker services and any standalone cleanup/import commands. Confirm no older task remains running and prevent automated restarts of those images. Keep both services stopped through recovery bootstrap and validation.
6. Create and review a recovery-only plan with the targets below. Verify the plan does not start or update either stopped service, change unrelated resources, or expose secret values. Apply only that approved saved plan. These targets include their dependencies; stop and resolve unexpected dependency changes before applying.

   ```powershell
   terraform plan -out=attachment-recovery.tfplan `
     -target=module.platform.aws_iam_role_policy_attachment.github_deploy_attachment_maintenance `
     -target=module.platform.aws_cloudwatch_event_target.attachment_maintenance `
     -target=module.platform.aws_cloudwatch_event_target.attachment_maintenance_failures `
     -target=module.platform.aws_cloudwatch_metric_alarm.attachment_maintenance_delivery_failed `
     -target=module.platform.aws_cloudwatch_metric_alarm.attachment_maintenance_failed `
     -target=module.platform.aws_cloudwatch_metric_alarm.attachment_maintenance_overdue
   terraform apply attachment-recovery.tfplan
   ```

7. Read `terraform output -json attachment_maintenance`; it must be nonnull. In EventBridge confirm its rule is `ENABLED`, its interval is `rate(1 day)`, and its ECS target names the new task revision. In ECS, run that exact `task_definition_arn` manually once as Fargate using the environment's existing cluster, private subnets, ECS security group, and public IP disabled. This is real cleanup and must be run only by the authorized operator. Wait for STOPPED; require container exit code `0` and `attachment_maintenance status=finished` with `failures=0 capped=false` in `/ecs/<environment-prefix>/backend`, stream prefix `attachment-maintenance`. If any check fails, keep services stopped while repairing recovery or follow the rollback procedure below.
8. Confirm all three named CloudWatch alarms exist even when the environment's optional general alarms are disabled. Check the failure-event log group's resource policy and target. Test the failure and success rules' event patterns in the EventBridge console using synthetic STOPPED task events for this exact family: startup failure and nonzero exit must match the failure rule; exit `0` with `EssentialContainerExited` must match only the success rule. Verify a different company environment's cluster and a different task family do not match. This pattern test launches no task and touches no data. The overdue alarm can initially be ALARM until the first successful run supplies its metric.
9. After recovery is proven, review and apply the ordinary complete release plan with the same immutable image/revision. Resume services only on the new image and confirm no old task was restarted. The API service depends on the daily target and failure reporting in Terraform. The QA email worker may remain disabled. Confirm the enabled rule still points at the released task revision, and verify the next daily run completes successfully. Do not describe recovery as active based only on a source file or successful API startup.

Future normal Terraform releases update the recovery task and target together with the backend image. The scoped deploy policy permits exact recovery rule/target, inline execution-permission, and alarm updates; initial creation or later changes to the IAM role/log resource policy remain a human SSO bootstrap responsibility. The schedule has no disabled default or email-worker prerequisite.

## Failure handling

`<environment-prefix>-attachment-maintenance-delivery-failed` alarms when EventBridge cannot invoke ECS after at most two retries within one hour. `<environment-prefix>-attachment-maintenance-failed` alarms on a matching failed STOPPED task event, including startup failures, interrupted tasks, and nonzero container exits. `<environment-prefix>-attachment-maintenance-overdue` alarms after 26 consecutive hourly periods without a successful exit; this also catches an absent/disabled target or ECS returning placement failures without starting a task. ECS failure events across revisions are retained in `/ecs/<environment-prefix>/attachment-maintenance-failures`; application item failures log company, attachment, and stage in the backend log group. Alarm metrics come from AWS events and do not query the application database. [AWS documents the event metrics](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-monitoring.html), [ECS task events](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_task_events.html), and [RunTask's separate failures response](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_RunTask.html).

Inspect launch permissions/network/image/secret-delivery failures through the task event and normal cleanup failures through the item stage. Pending rows and keys survive failures. After fixing the cause, rerun the exact one-shot task and require exit `0`. An item cap requires additional finite runs; completed rows disappear from the next run, while failed rows remain available. Do not clear deletion markers, delete rows by hand, or manually delete shared objects to quiet an alarm. A persistent failed item needs its underlying cause repaired. Alarm actions are optional and must not be confused with an active human notification channel.

Rolling back to an image without the shared lock also requires an approved maintenance window. Disable the daily target, drain and stop all new API/email-worker and standalone cleanup/import processes, and confirm every maintenance task has stopped before restarting the prior images with their original deletion timer. Do not leave new recovery running beside an older API or email worker, and do not run the maintenance role on an older image that does not recognize it. Review the rollback plan before changing the shared backend image input.

## Isolated verification

`node scripts/test_attachment_cleanup_postgres.mjs` creates and removes its own disposable local PostgreSQL cluster and uses mocked object storage; it accepts no live database URL. On Windows it runs the Go test through WSL Ubuntu and `/usr/local/go/bin/go`, so use the approved outside-sandbox execution path. The fixture exercises canonical schema and the index migration, owner deletion, recycle/restore/purge, shared keys, partial storage/database failures, duplicate consumers, backlog continuation, and an 87,270-row query plan. Run `node --test --test-isolation=none infra/tests/attachment_maintenance.test.mjs` for the static recovery wiring contract. These checks do not deploy recovery or authorize live cleanup.
