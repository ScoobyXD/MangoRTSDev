# Current Email Business Logic Laws

1. Every newly created Mango user has `mailbox_enabled=false`.
2. Only users with `mailbox_enabled=true` may connect a mailbox or use personal or shared inbox APIs and realtime subscriptions, regardless of their company role.
3. Mailbox-disabled users cannot read or write attached-email records, email-selected chats, or email-owned files through Node or Project access.
4. Mailbox-disabled resource reads preserve ordinary work, chats, files, and omitted-history totals while omitting attached-email rows, email-selected chats, and derived textbox email links.
5. A disabled personal mailbox cannot enter provider ingestion, reconciliation, archive work, or webhook processing.
6. Existing enabled users and company-owned shared connections retain the email behavior below.
7. Account confirmation, password recovery, and company invitation messages remain separate from mailbox ingestion and Nylas.
8. An OAuth callback must resolve its exact original Mango user and mailbox eligibility before exchanging a provider code; an email match never substitutes another user identity.
9. Email exists to distribute messages into useful Nodes and Projects, discuss exact messages in their text boxes, preserve personal mailbox drafts, and let exact Nodes or Projects own one shared Reply draft per attached source message.
10. Selecting a Node in the email Universal Linker adds the email to that existing Node.
11. Selecting a Logic Gate immediately creates a new email Node in that Logic Gate with priority **Not Assigned**.
12. Selecting a Project requires one Project Logic Gate choice, then creates a new email Node there with priority **Not Assigned**.
13. One stored email thread may belong to multiple Nodes and Projects, and each Node or Project may contain multiple stored email threads.
14. Every newly ingested message inherits every Node-wide and Project-wide destination already used by its thread.
15. New-message ingestion never creates or copies a text-box relationship, chat, or draft.
16. An email thread never links to a text box; only exact email messages link to text boxes, and several exact messages may share one text box.
17. One exact email message may link to at most one text box per Node or Project and may use different text boxes in different owners.
18. Every email chat belongs to one exact Node or Project, one exact textbox in that resource, and one exact linked email message. Mango does not create unlinked email chats.
19. Chats about the same message in different Nodes remain separate.
20. Highlighting email text only shows the **Turn highlighted email text into a chat** action. Clicking it keeps the exact quote visibly highlighted and stages the exact Node or Project textbox destination without writing to the database.
21. If the chosen Node or Project already links that message to the chosen textbox, the chat appends there. Otherwise the first send atomically links the chosen existing textbox or creates the staged textbox, then creates the exact chat.
22. If a triage thread has no Node, the first sent chat creates a floating Node with priority **Not Assigned** and no popup. If the thread has several Nodes, the user chooses the destination Node before send.
23. Clearing the quote or closing its unsent rail cancels the preview without creating or deleting database rows.
24. My Triage and Shared Triage show one scrollable chat rail for the thread, grouped only by exact Node and text box; different messages in that same Node/text box do not create separators.
25. Each triage chat group header shows a clickable Node icon and Node title.
26. The chat rail opens automatically when the selected thread already has accessible chats. The email thread header owns the one neutral manual toggle. Individual messages show no chat button or three-dot overflow button.
27. The chat rail's top and bottom borders align with the displayed email-message card, not the subject and action toolbar above that card.
28. In a Node, dragging only the noninteractive header of one exact message onto a text box creates that exact textbox relationship without a chat; message bodies, selected text, buttons, links, and inputs never start the drag.
29. For an exact ingested Node or Project message with retained mailbox provenance, Reply opens personal **My Draft** by default. With effective Edit to that exact resource, checking **Shared Draft** creates or opens the resource-shared Reply; unchecking returns to **My Draft** without deleting either. Both use the existing rich composer and `email_draft` attachment controls, while Reply All, Forward, and scheduling remain absent.
30. Opening, expanding, refreshing, or navigating Node or Project email reads the stored message through that exact resource and durable email relationship without requiring the viewer's connected personal account to match the saved source account. It performs no outbound work, draft mutation, draft-body read, or draft-attachment relationship read. One bounded body-free grouped read may return separate personal and shared indicators and thread totals for all visible exact messages; an unavailable draft scope produces no indicator and never replaces the stored view with an error. Reply/**My Draft** exact-hydrates the personal draft, while only checking **Shared Draft** or opening an exact shared summary exact-hydrates the shared draft.
31. Node email views retain received-message bodies and attachments, thread expansion, exact-message loading, highlights, selection chats, and calendar invitation responses. Every stored-thread message header in the Node email column always shows a horizontal textbox-plus control that creates or reuses that exact message's textbox; only a linked message shows an adjacent textbox-navigation control, and message disclosure never navigates to a textbox.
32. My Triage and Shared Triage retain New compose, Reply, Reply All, Forward, creator-owned mailbox drafts, signatures, attachments, scheduling, and safe send. Their lower row has four equal controls in one line or clean wrap: **Compose**, **My Drafts**, **Shared Drafts**, and **Archive & next**.
33. Reply and Reply All require an internal `email_message_id`; Node and Project likewise enable Reply only when the displayed source has that ingested identity and stored exact-mailbox provenance, and clicking Reply never imports a provider-only message.
34. A personal Reply draft belongs to one exact creator, exact personal-account or shared-inbox scope, and exact internal source message and remains owner-only. A resource-shared Reply stores the literal `shared_resource_type + shared_resource_id` pair and belongs to one exact company, Node or Project, and internal source message; its creator is audit metadata, and both drafts may coexist.
35. Effective Edit access to the exact Node or Project is required to list, summarize, open, create, edit, attach to, discard, or use a restored resource-shared draft. Node and Project use the same rule, every command rechecks it, and personal draft authorization remains unchanged.
36. Reply uses the canonical reply address. Reply All de-duplicates recipients and excludes the active sender account. The server derives the Reply draft sender and reply target from the exact ingested source and fixes **From** read-only. Resource-shared editing grants no sender right: send separately requires current exact personal-mailbox ownership or exact Shared Inbox send/Edit authority and rechecks it before attachment or provider work.
37. A sent reply becomes a new message in the same thread and inherits every Node-wide destination already used by that thread.
38. Closing a Triage, Node, or Project reply surface flushes and preserves the latest active exact personal or resource-shared draft. Checking **Shared Draft** seeds the current persisted personal body and attachment links only when creating the shared draft for the first time; an existing shared draft is never overwritten, and unchecking performs no delete. Resource-shared text saves and attachment mutations require the expected revision; a stale revision returns one HTTP 409 conflict without automatic reload or retry, and explicit discard removes only the active exact authorized draft.
39. Opening, closing, or refreshing the triage chat rail does not restart or revoke an unchanged inline email image source.
40. A triage chat send reuses the exact mailbox-scoped stored message when present, otherwise fetches and stores only that exact provider message, and never calls triage conversion or queues remaining-thread ingestion.
41. A My Triage or Shared Triage send adds the chat to the open rail before the request starts; success keeps the optimistic row, and failure removes it and restores the composer.
42. Once an exact email message already has a Node text box, each later triage chat uses only the normal Node text-box-chat create command.
43. A Node opens with every attached-email thread collapsed. One bounded grouped read supplies body-free personal and shared draft indicators and separate thread totals for the visible exact messages. Opening one message loads only its stored body and received-attachment metadata; Reply/**My Draft** loads the personal draft, while checking **Shared Draft** or opening an exact shared summary loads only that shared draft and its attachment relationships.
44. A chat authored by the current user moves the shared message view to the new message at the bottom.
45. Every saved email-selection chat renders its exact stored quote and offsets as a lasting highlight in My Triage, Shared Triage, and Node email views.
46. My Triage and Shared Triage enrich each provider mailbox row with its exact stored `email_message_id` and `email_thread_id` by matching the exact company, email connection, and provider message ID. A successful send returns its newly persisted message with those same durable IDs before Mango inserts that Sent row into a mailbox list. Provider-list, immediate-sent, scheduled-sent, and stored-detail copies all keep the same exact mailbox source scope, so re-selecting the active row cannot change its client identity or clear its loaded conversation. Collaboration decoration never supplies or replaces those identities. Triage trusts the durable identity only when both IDs are present and otherwise ingests the one exact selected provider message before reading its stored thread. Stored-thread readers use only the durable `email_thread_id` and render every returned stored message summary once in `message_order`; Node views fetch a complete body only for the exact opened message, and display membership never comes from provider thread IDs, locally remembered replies, collaborations, or provider preview pages.
47. A one-hash email reference stores its exact durable `email_message_id`, durable `email_thread_id`, and only its personal-account or shared-inbox authorization scope. One ordinary click from every supported editor surface opens the same stored-thread read and renderer in the existing quick modal, independent of resource relationships; it creates no relationship, email route, provider lookup, mailbox-page search, or second email-rendering system.
48. A quoted copy of an earlier email inside another message body is body content only. Every email viewer collapses reliably detected quoted history by default behind **Show subthread**, which reveals that exact message's complete stored body without changing thread membership. Quoted body content never permits Mango to omit an earlier stored message row.
49. A Project displays attached threads in one Project-wide email column. Highlighting an unlinked exact internal message defaults to **Existing Project · New Text Box**; clicking an eligible timeline textbox moves the same unsent composer to **Existing Project · Existing Text Box**, and the first send atomically creates the exact Project/textbox/message relationship and chat. The permanent Project document is never eligible.
50. Automatic ingestion accepts a post-activation trigger only when that exact provider message is in Inbox or Sent, then reconciles every real member of that provider thread into one durable thread under the exact email connection. Archive-, Draft-, Trash-, Spam-, and other folder-only triggers remain ineligible; another connection's copy never qualifies or merges with it.
51. Mango sends to and receives from external email addresses without requiring a Mango user or contact. To, Cc, and Bcc accept any syntactically valid address, company users are suggestions only, and Send or Save commits valid address text still pending in a recipient field.
52. A Node or Project textbox's email control shows every exact linked message oldest-to-newest by stored message timestamp; linking another message never replaces or hides an earlier linked message and never changes the normal stored-thread message list.
53. The Node or Project textbox's permanent server-owned `color` decorates each exact linked message card, while the outer thread card remains neutral because a thread never links to a textbox.
54. Frontend `linkedEmailMessageIDs` is derived only from the backend Node or Project textbox projection's ordered `email_message_ids`, is never serialized as textbox metadata, never scans attached threads to infer or reorder membership, and never accepts a provider message ID or singular representative as relationship authority.
55. The explicit remove control beside one exact message removes only its Node or Project textbox relationship when no chat in that textbox is anchored to that message; removing one of several keeps the textbox color, removing the last returns the textbox to neutral, and a guarded rejection changes neither relationships nor color.
56. While a highlighted-email chat is pending in a Node, each eligible textbox-header click moves the same pending composer and draft and replaces its destination until the first successful Send, without writing before Send; an authoritative existing link remains the only allowed destination in that Node.
57. Opening **My Drafts** keeps its existing summary pagination, search, and order. Opening **Shared Drafts** returns body-free summaries only for accessible Node and Project shared drafts in the selected exact mailbox; visible-message indicators are likewise one bounded grouped read. Opening any draft or sending one personal scheduled draft loads only that exact draft and its attachments.
58. Missing sources, denied mailbox access, disconnected senders, and invalid draft fields use separate error codes.
59. A Node-wide or Project-wide email relationship cannot be removed while that exact owner and thread have a textbox-specific relationship or email-selection chat; the owner-specific guard changes nothing.
60. A permitted Node-wide or Project-wide email removal deletes the exact relationship and retires only that owner's exact resource-shared draft and its draft attachment links, with no later revival from simply relinking the email. Recycling a Node or Project instead captures its shared drafts and links; restoring that same owner revives only those captured rows after its wide relationships and advances each draft to a fresh revision. Permanent deletion has no restore. No path deletes the stored thread, message, another owner's edge or shared draft, any personal draft, received attachment, textbox, chat, or attachment with another live owner.
61. Every outbound My Triage, Shared Triage, Node, or Project action uses the existing ten-second safe-send bar with **Send now** and **Undo** and the existing provider/persistence send tail. The gate starts at most one HTTP dispatch for each pending browser attempt, adds no durable send lease/state machine, and does not claim provider-level exactly-once delivery; success promotes attachment links, records the sent message, and deletes its durable draft, while failure retains it.
62. Ordinary Node or Project email viewing never enters the outbound safe-send path; only an explicit exact-message Reply enters it, and Undo starts no provider send.
63. The sidebar must not request mailbox status at startup; mailbox lists and account suggestions load only when their mailbox controls need them.
64. Home Updates and RACI must load independently of mailbox status or configuration; mailbox lists, drafts, and signatures load only for eligible Mail views or opened mail controls, while existing eligible users keep their scheduled sending behavior.

## Process Story

A new account confirms its identity and enters Mango with mailbox features disabled. Creating or joining a company preserves that restriction. Ordinary work remains available without Google or Nylas. Existing enabled users continue using their authorized mailboxes and stored email work; company-owned background mail processing continues independently. The server enforces eligibility for provider callbacks, direct API access, stored email surfaces, subscriptions, and personal background work.

## Scenario 1: A new user joins an existing company

The user signs up without a provider connection and later accepts a company-admin invitation. Personal and shared mailbox requests return `mailbox_disabled`, including direct URLs and subscriptions. Node and Project reads retain normal documents, chats, and files while omitting mailbox records and derived email links.

## Scenario 2: Existing mailbox work continues

An enabled existing user opens an authorized personal or shared inbox, reads an attached stored message, and replies through the existing draft and send rules. The original account, company permissions, resource permissions, exact message identity, and attachment ownership remain authoritative. A newly invited mailbox-disabled colleague does not gain mailbox access through that company.

## Scenario 3: A stale provider request or queued job arrives

An OAuth callback for a missing or disabled exact user exchanges no provider code. A disabled personal connection schedules no ingestion and makes no provider call during delivery or reconciliation; its webhook is ignored. An existing company-owned shared connection continues processing under its existing rules.

Detailed draft and file behavior is also governed by [email drafts and shared replies](email%20drafts%26shared.md), [attachments](attachments.md), and [relationships](relationships.md).
