# CtrlLoop provider contracts

Managed Agents MCP uses the existing OpenAI client. Its optional `MCPTool` argument sends `type=mcp`, `server_label`, `connection_origin=service`, an explicit `allowed_tools` list, and `required=true`. Its `transport` is `{type:http,server_url:<HTTPS URL>,authorization:Bearer <run token>}` with optional authenticated headers. Ordinary function sessions keep their existing schema and `environment.type=none`. The run token belongs only in transport authorization, never instructions, input, logs, or browser responses. The service URL must be reachable from OpenAI; local-only addresses cannot serve a deployed service connection. See the [official managed Agents MCP guide](https://developers.openai.com/api/docs/guides/agents-api/tools/mcp).

The worker reads one exact message from its authorized grant through the existing Nylas request gate and rejects a response with a different message ID. The source resolver validates its provider URL and receipt timestamp; only Excel `Apply` formats the arrival text in the job's timezone. Nylas documents provider-native Google/Microsoft IDs in [Get a message thread](https://developer.nylas.com/docs/cookbook/email/get-message-thread/) and Microsoft immutable IDs in [Search best practices](https://developer.nylas.com/docs/dev-guide/best-practices/search/). This does not authorize using an arbitrary Nylas UUID as a provider ID.

The [official Nylas SDK message model](https://github.com/nylas/nylas-nodejs/blob/main/src/models/messages.ts) defines `date` as receipt by the mail server, separate from the unverified RFC Date header. CtrlLoop converts that epoch to the configured IANA timezone and writes literal text such as `9/13/26 2:31PM`. It never uses processing time, webhook time, or an Excel numeric date. Bundled IANA data makes this independent of host timezone files.

Microsoft source links use the exact URL-encoded native message ID in `https://outlook.office.com/mail/deeplink/read/<id>`, a route [documented by Microsoft support staff](https://learn.microsoft.com/en-my/answers/questions/5508811/outlook-web-deeplink-retrieves-subject-of-email-bu). The route requires the correct provider sign-in. No undocumented account selector is added. [Microsoft Graph documents `webLink`](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0), but the existing Nylas message API does not expose that property. Opening real Nylas immutable IDs in Outlook, including moved messages and multiple signed-in mailboxes, still requires a provider-browser smoke test; mocked builder tests do not establish that behavior.

Gmail remains unresolved at this point. Its [REST message model](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages) returns native hexadecimal IDs without a browser permalink. [Apps Script `GmailThread.getPermalink`](https://developers.google.com/apps-script/reference/gmail/gmail-thread#getpermalink) supplies a permalink but is not callable using the existing Nylas grant. A [current Google Workspace CLI issue](https://github.com/googleworkspace/cli/issues/858) reports that legacy `#all/<hex>` links fail from a cold browser load. Print-view and account-selection URL candidates have not been verified as a supported direct-link contract. Until a usable provider link is established, the resolver returns an explicit Gmail error before workbook updates. It supplies no search URL, synthetic provider ID, or Mango email viewer.

Verification uses synthetic messages and mocked provider requests only. No production credentials, customer email, provider settings, or live database writes were used.
